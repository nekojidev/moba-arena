## а) Клієнт зникає посеред матчу

У кімнаті 5 гравців, HEARTBEAT_MS=1000 (у продакшені типово 15000 — часи нижче масштабуються разом із ним).

| Що сталося                                        | Через скільки сервер прибрав гравця      |
| ------------------------------------------------- | ---------------------------------------- |
| сокет знищено без кадру закриття (ОС закрила TCP) | 5 мс                                     |
| клієнт «завис»: TCP живий, на ping не відповідає  | 2452.7 мс (вікно heartbeat — до 3000 мс) |

Після цього: гравців у кімнаті 3, матчів 1, з’єднань 3; лічильник `moba_rejections_total{reason="heartbeat_lost"}` = 1. Матч іде далі: 30 кроків за секунду, решта гравців отримала 40, 40, 40 кадрів за секунду; жодного з них не від’єднано (0).

Знищений сокет сервер помічає одразу, бо ОС надсилає FIN/RST. Heartbeat потрібен для другого випадку, коли «з того боку» просто тиша: гравця прибирають після двох пропущених pong, тобто за 2–3 періоди ping.

## б) Сервер убито посеред матчу (SIGKILL) і запущено знову

4 безголових клієнтів на справжньому `client/src/net/connection.ts` (типові паузи: 0,5 с → 1 → 2 → 4 → 8 с, із jitter). «Платформа» запускає процес знову через 1000 мс після вбивства.

| Показник                                                   | Значення                                                        |
| ---------------------------------------------------------- | --------------------------------------------------------------- |
| сервер недоступний (від SIGKILL до першого 200 на /health) | 1177 мс                                                         |
| клієнти знову в кімнаті (від SIGKILL до нового welcome)    | 1507–2646 мс                                                    |
| з цього очікування клієнта вже після підняття сервера      | до 1470 мс                                                      |
| невдалих спроб на клієнта                                  | 2, 3, 3, 3                                                      |
| паузи між спробами, мс                                     | 496 → 959; 339 → 612 → 1241; 484 → 548 → 1206; 372 → 588 → 1664 |

Усі клієнти повернулися самі (стан з’єднань: open), гравців у кімнаті знову 4. Але це НОВИЙ матч: сервер тримає стан лише в пам’яті, тож лічильник кроків почався з нуля (було 90, стало 49), рахунок утрачено, а гравці отримали нові id. Час відновлення складається з часу перезапуску і паузи, на якій клієнт саме стояв: що довше сервер лежить, то довша наступна пауза (до 8 с).

У браузері гравець при цьому не лишається перед завмерлою грою: після чотирьох невдалих спроб поспіль (або одразу після повідомлення `shutdown` під час штатної зупинки) клієнт зупиняє гру й повертає його в лобі з поясненням — цю логіку перевіряє `client/test/session.test.js`.

### Що ці числа показують насправді

Сервер однопотоковий: кімнати A і B ділять один цикл подій. «Тривалість кроку» — це час самого обчислення кроку кімнати B; сміття в кімнаті A на неї майже не впливає, бо розбір чужих кадрів відбувається МІЖ кроками, а не всередині них. Тому чесніший показник — «запізнення»: на скільки пізніше за розклад крок почався, бо цикл подій був зайнятий чужою роботою (розбір сміття, рукостискання, вхід і вихід нападника з кімнати A, записи в лог). Поруч — частка часу, коли цикл подій був зайнятий: саме вона показує ціну потоку (6.3 % → 28.8 % → 5 %). Різниця в частках мілісекунди між фазами (зокрема коли «під час» виходить МЕНШЕ, ніж «до») — шум вимірювання й розігрів JIT, а не ефект потоку. Ізоляції між кімнатами немає: достатньо потужний потік (або багато нападників з різних адрес) зрештою затримає кроки всіх кімнат. Захист тут — зробити кожен зіпсований кадр дешевим (закриття на першому, решта не розбирається) і обмежити кількість з’єднань з однієї адреси (`MAX_CONNECTIONS_PER_IP`); справжня ізоляція потребує окремих процесів або worker-потоків на кімнату.
